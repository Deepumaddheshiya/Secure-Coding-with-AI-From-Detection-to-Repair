# Research Paper Analysis: Secure Coding with AI — From Detection to Repair

**Original Article:**  
Vladislav Belozerov, Peter J. Barclay, and Ashkan Sami  
*Secure coding with AI – from detection to repair*  
**Journal:** *Empirical Software Engineering* (2026) 31:93  
**DOI:** [10.1007/s10664-026-10812-8](https://doi.org/10.1007/s10664-026-10812-8)

---

## 1. Executive Summary & Objectives

The research investigates the security posture of software code generated by Large Language Models (LLMs) extracted from developer interactions in the **DevGPT dataset**. It evaluates the dual capability of LLMs to:
1. **Detect** software vulnerabilities in real-world code.
2. **Repair** detected vulnerabilities automatically.

The study investigates C-family languages (**C, C++, and C#**), subjecting 2,315 code snippets across two snapshots to a multi-scanner static analysis pipeline (Flawfinder, Semgrep, Snyk, Cppcheck), followed by expert manual verification, and longitudinal evaluation across two generations of frontier LLMs (October 2024 vs. September 2025).

---

## 2. Research Questions (RQs) & Core Findings

### RQ1: How secure is the code generated by GPT in the DevGPT dataset?
- **Dataset Scale:** 2,315 source files analyzed (325 C, 990 C++, 1,000 C#).
- **Scanner Pre-filtering:** 114 files flagged by at least one scanner as potentially vulnerable.
- **Manual Verification:** Of the 114 flagged files, **56 confirmed vulnerabilities** were identified across **48 files** (the remaining were false positives, e.g., safe `const char*` pointers in `printf`, pre-validated `memcpy` bounds).
- **CWE Distribution:** 23 distinct CWE types across 66 assigned instances (Table 8).
  - Top CWEs: **CWE-20** (Improper Input Validation, 16 instances), **CWE-120** (Classic Buffer Overflow, 11 instances), **CWE-362** (Race Condition, 7 instances), **CWE-119** (Memory Buffer Bounds, 4 instances).
- **Language Vulnerability Density (Table 9):**
  - **C:** Least secure, 10.4 Lines of Code (LOC) per detection.
  - **C++:** Intermediate, 83.8 LOC per detection.
  - **C#:** Most secure, 2,937.5 LOC per detection.

### RQ2: How effective are LLMs in detecting and correcting security issues when explicitly asked to do so?
- **October 2024 Experiment (GPT-4o, default temperature 1.0):**
  - Evaluated on 32 confirmed issues in 26 files (from `snapshot_20231012`).
  - **Detected:** 18 / 32 issues (**56.25%**).
  - **Fixed:** 17 / 32 issues (**53.13%**).
  - *Conclusion:* Inadequate for autonomous security analysis; prone to overlooking subtle memory issues.
- **September 2025 Experiment (GPT-4.1, GPT-5, Claude Opus 4.1):**
  - Evaluated on all 56 confirmed issues in 48 files (both snapshots).
  - **GPT-4.1 (temp 0.1):** Detected 46/56 (**82.14%**), Repaired 42/56 (**75.00%**).
  - **GPT-5 (temp 1.0):** Detected 44/56 (**78.57%**), Repaired 44/56 (**78.57%**).
  - **Claude Opus 4.1 (temp 0.1):** Detected 45/56 (**80.36%**), Repaired 43/56 (**76.79%**).
  - *Key Improvement:* Detection rates jumped from ~56% to ~80%, fix rates from ~53% to ~77%.

### RQ3: Do developers provide more vulnerable code, or does GPT generate more insecure code during interactions?
- **Provenance Breakdown (Table 17 & 18):**
  - **User-Provided Prompts:** 23 files, **25 confirmed vulnerabilities** (44.6%).
  - **GPT-Generated Responses:** 25 files, **31 confirmed vulnerabilities** (55.4%).
- **Model Repair Performance by Origin:**
  - On User-written code: Models achieved **88%** (GPT-4.1), **84%** (GPT-5), **76%** (Claude Opus 4.1) repair success.
  - On GPT-generated code: Models achieved **74.19%** (GPT-4.1), **74.19%** (GPT-5), **80.65%** (Claude Opus 4.1).
  - *Finding:* LLMs reason about and correct human-written code slightly better than self-inspecting AI-generated code.

## 3. Methodological Nuances & Paper Insights

1. **AI Sycophancy & Hallucinated CWEs:**
   The paper documents that LLMs frequently flag non-existent vulnerabilities and invent plausible-sounding CWEs (e.g. Listing 1 in paper: a harmless single-line `fprintf(stderr, "Log\n")` was flagged with CWE-134, CWE-532, CWE-117, CWE-252, CWE-400 by GPT-4.1, GPT-5, and Claude Opus).
2. **Overconfidence:**
   LLMs present incorrect findings with authoritative tone. Thus, automated AI output must never be treated as ground truth without compiler checks, security re-scans, and human audit trails.
3. **Prompting Strategy:**
   Zero-shot prompting was selected to mirror real-world developer interactions without exemplars that could bias the model toward specific vulnerability patterns.
